# SWUFE HotelSim 项目完整介绍

版本日期：2026-08-06
适用对象：项目负责人、课程教师、后续接手开发者、部署运维人员、项目验收人员

## 1. 项目概述

SWUFE HotelSim 是一个面向教学与经营管理竞赛的酒店经营模拟平台，目标是为学生、教师、赛事管理员、评委与观众提供完整、可闭环、可验证的业务系统。项目围绕“赛事组织、班级与团队、经营决策、模拟处理、评审评分、公开传播、平台治理”构建全流程应用。

该系统当前已经具备以下核心特征：

- 支持学生、教师、管理员、评委与观众场景的真实登录和权限分流。
- 支持学期、班级、团队、成员、轮次、经营决策、模拟结果、教师评分等核心业务对象。
- 支持教师初始化轮次、学生提交经营决策、教师处理轮次、学生查看结果和排名、教师评分的完整业务闭环。
- 支持管理员进行用户治理、学期治理、班级治理、队伍与名册管理、CSV 批量导入导出。
- 支持审计日志、可观测性看板、可执行告警、告警确认/静默、站外告警投递等运营增强能力。
- 支持可抛弃的 Supabase fresh disposable 环境全链回归验证。

截至当前版本，项目已经实现到“可运行、可演示、可交接、可继续增强”的状态。换言之，当前项目已经不是原型，而是一套具备真实业务链、交付能力与运维收口的课程模拟平台基线版本。

## 3. 项目定位与使用场景

本项目主要面向以下使用场景：

### 3.1 教学使用场景

- 教师创建学期与班级，组织学生进入课程。
- 学生以团队形式扮演酒店经营者，按轮次提交经营决策。
- 系统依据内置经营模拟引擎计算营收、利润、入住率、品牌与 ESG 等指标。
- 教师对已处理轮次的团队进行评分和评语反馈。
- 学生基于结果、排行榜和教师反馈进行复盘。

### 3.2 管理与治理场景

- 管理员统一管理平台用户、学期归属、班级全景和队伍名册。
- 管理员可通过 CSV 批量导入/导出班级名册，提高教学准备效率。
- 管理员可查看最近审计活动、实时可观测性数据和可执行告警。

### 3.3 项目交接与运维场景

- 项目使用 Prisma + Supabase 作为数据库与迁移基础设施，便于接手者继续扩展。
- 文档、E2E、Seed、Runbook 已同步建设，可用于后续部署、回归与交接。

## 4. 技术架构与选型

### 4.1 前端与全栈框架

- 框架：Next.js 15.5
- 语言：TypeScript
- 路由模式：App Router
- 样式：Tailwind CSS
- 状态与数据请求：TanStack React Query
- 图表：Recharts
- UI 组织方式：按角色工作区拆分页面，并通过共享 workspace shell 统一体验

### 4.2 后端与数据层

- ORM：Prisma
- 数据库：Supabase Postgres
- 权限配套：Supabase RLS SQL 文件纳入仓库
- 身份认证：Auth.js / NextAuth
- 密码处理：`bcryptjs`
- 校验：`zod`

### 4.3 测试体系

- 单元/组件/路由测试：Vitest + Testing Library
- E2E：Playwright
- 类型检查：TypeScript `tsc --noEmit`
- 代码规范：ESLint

### 4.4 架构分层

项目采用“页面层 + 组件层 + API 层 + DAL 层 + Prisma 数据层”的组织方式：

- `src/app/*`：路由页面与 API Route。
- `src/components/*`：角色业务面板、共享壳层、认证组件、图表与局部交互。
- `src/lib/dal/*`：数据访问边界，供 API 与服务逻辑复用。
- `src/lib/simulation/*`：模拟引擎与轮次处理辅助逻辑。
- `prisma/*`：数据模型、迁移与种子脚本。
- `supabase/*`：RLS 与 CLI 配套文件。

这样的组织方式具有几个优点：

- 页面代码保持薄层，业务逻辑集中。
- API Route 不直接堆叠复杂 SQL，而是通过 DAL 复用访问逻辑。
- 后续接手者可以比较明确地找到“改页面”“改接口”“改公式”“改数据结构”的入口。

## 5. 核心数据模型

项目目前已经建立起一套比较完整的数据对象关系：

- `User`：平台用户，支持学生、教师、管理员、评委与观众角色。
- `Semester`：学期或教学窗口，是班级的上层容器。
- `Class`：具体课程班级，包含轮次配置、房量与模拟参数。
- `Team`：学生团队，对应一间模拟酒店的经营主体。
- `TeamMember`：团队成员与班级成员关系，同时约束“同一学生在同一班级只能属于一个队伍”。
- `HotelState`：跨轮次延续的酒店状态，如现金、负债、品牌、满意度、ESG、员工状态等。
- `Round`：模拟轮次，记录当前轮编号、状态、截止时间、外部环境因子。
- `Decision`：某个团队在某个轮次提交的经营决策。
- `RoundResult`：轮次处理后的结果记录，包括财务指标、市场表现、排名和教师评分。
- `Competition` / `CompetitionStage`：赛事及阶段，承载赛事生命周期和回合归属。
- `CompetitionJudgeAssignment` / `JudgeScore`：赛事级评委授权与独立评审记录。
- `SystemConfig`：用于承载部分系统级配置与告警状态持久化。

这套数据模型已经能支撑“教学组织层 + 经营模拟层 + 管理运营层”三类能力的并行发展。

## 7. 关键实现原理

### 7.1 权限与访问控制原理

系统采用“认证会话 + 角色守卫 + 数据访问控制”的组合方式：

- 用户登录后获得会话。
- 页面级守卫根据角色限制访问路径。
- API 层在写操作前再次校验权限。
- Supabase RLS 与应用层约束共同保护数据安全。

这种双层保护方式有助于避免“页面可见但接口仍可越权调用”的情况。

### 7.2 API 与 DAL 分层原理

系统 API 不直接将所有数据库逻辑写死在 Route 中，而是通过 DAL 层组织访问逻辑。其好处包括：

- 便于多处复用同一数据读取和写入逻辑。
- 降低页面、接口与数据库访问耦合。
- 后续如果要替换实现或补充缓存，更容易演进。

当前已存在的 API 覆盖范围包括：

- 认证 API
- `semesters`
- `classes`
- `teams`
- `decisions`
- `rounds`
- `simulation/run`
- `simulation/results`
- `grading`
- `export`
- `export/grades`
- `users`
- `roster/csv`
- `audit-logs`
- `observability`
- `alerts`
- `alerts/state`
- `alerts/deliver`

### 7.3 轮次推进原理

教师点击“初始化”或“处理轮次”后，系统按以下原则推进：

1. 先校验班级与轮次状态是否合法。
2. 若是处理动作，则检查当前轮必须为 `PENDING`。
3. 检查所有团队都存在决策记录。
4. 检查所有决策都已经正式提交。
5. 检查每个团队都存在 `HotelState`。
6. 轮次状态先切换到 `PROCESSING`。
7. 调用模拟引擎进行计算。
8. 在事务中写入结果、更新酒店状态、锁定决策、完成轮次、生成下一轮。
9. 如果中途异常，则尽量把轮次状态回滚回 `PENDING`。

这说明当前实现不仅能算结果，也考虑了处理过程中的状态一致性。

### 7.4 核心算法原理

项目当前的核心算法是“酒店经营模拟引擎”。其目标不是做严格的经济学学术模拟，而是为教学场景提供一个稳定、可调参、可解释、可重复验证的经营结果生成机制。

算法核心步骤如下：

#### 7.4.1 市场需求建模

- 系统内置 8 个客源细分市场，例如商务散客、商务团队、休闲散客、OTA、长住等。
- 每个细分市场具有默认价格、价格弹性、营销敏感度、质量敏感度和季节曲线。
- 每个轮次又带有季节因子、经济因子、事件因子。
- 系统据此计算本轮的总市场需求和各细分市场需求。

#### 7.4.2 团队竞争力建模

对每一个团队，系统会基于以下因素计算在每个细分市场的吸引力：

- 定价策略
- 对该细分市场的营销预算配置
- 渠道结构与该细分市场的匹配度
- 酒店当前质量状态
- 品牌与线上评分
- ESG 表现

然后将各团队的吸引力归一化，得到细分市场份额分配。

#### 7.4.3 容量约束与经营结果

系统不会无限放大需求，而会受到房量与房晚容量约束。处理后可得到：

- 房晚销量
- 入住率
- ADR
- RevPAR
- 分市场营收
- 客房总营收

#### 7.4.4 财务结果与酒店状态滚动

系统会继续计算：

- 餐饮及其他收入
- 营销费用
- 运营费用
- 折旧、利息、税费
- 净利润
- 现金余额
- 总负债
- 资产与质量状态变化
- 品牌、满意度、线上评分、ESG、员工士气等变化

因此，系统并不是只生成一个简单排名，而是维护了一个跨轮演化的酒店经营状态。

#### 7.4.5 排名机制

系统当前已输出多维排名：

- 营收排名
- 利润排名
- 入住率排名
- 综合排名

综合排名基于经营表现与非财务指标的加权结果，用于更贴合教学评价场景。

#### 7.4.6 当前算法边界

当前算法已经可用，并完成了业务闭环接入，但仍保留进一步校准空间。例如：

- `basePropertyTaxRate`
- `vatRate`
- `randomnessFactor`

这些参数已经在配置结构中预留，但尚未全部正式纳入最终公式。也就是说，当前版本属于“可运行、可教学、可验证的业务算法版本”，而不是“已经完成最终学术口径标定的终版模型”。

### 7.5 品牌化与国际化原理

Stage 6 已将项目收口为“中文优先、兼容英文”的工作区体验：

- 首页与各角色工作区具备统一品牌语言。
- 学生、教师、管理员共享统一的 workspace shell。
- 状态标签做了独立映射与测试。
- 页面级 copy 经过整理，便于后续继续扩展中文文案或双语切换。

这种方式有利于在保留工程结构稳定性的前提下，逐步提升界面一致性与正式度。

## 8. 程序如何使用

### 8.1 本地开发启动

推荐流程如下：

```bash
pnpm install
pnpm db:generate
pnpm build
pnpm dev
```

在首次克隆后，建议额外执行一次：

```bash
pnpm typecheck
pnpm lint
pnpm test
```

### 8.2 数据库与 Supabase 使用

项目当前采用 Prisma-first 的数据库工作流：

- `prisma/schema.prisma` 是数据结构事实来源。
- 迁移通过 Prisma 管理。
- RLS 通过 `supabase/rls.sql` 应用。
- 种子数据通过 `prisma/seed.ts` 生成。

常用命令如下：

```bash
pnpm db:validate
pnpm db:generate
pnpm db:migrate
pnpm db:deploy
pnpm db:seed
pnpm db:rls
```

说明：

- 当前工作流不要求全局 Supabase CLI 登录。
- 如果只是走 Prisma 迁移与种子流程，通常不需要 `supabase login`。
- 只有在使用 `supabase link`、`supabase db pull` 等托管管理命令时，才需要 Token 型登录。

### 8.3 disposable 环境验证使用方式

当需要对可抛弃数据库做真实全链验证时，可按下列顺序执行：

```bash
ALLOW_DB_RESET=true pnpm db:seed
E2E_ALLOW_MUTATION=true E2E_EXPECT_FRESH_SEED=true pnpm test:e2e e2e/admin-governance-disposable-flow.spec.ts
E2E_ALLOW_MUTATION=true E2E_EXPECT_FRESH_SEED=true pnpm test:e2e e2e/admin-roster-live-flow.spec.ts
E2E_ALLOW_MUTATION=true E2E_EXPECT_FRESH_SEED=true pnpm test:e2e e2e/stage3-disposable-flow.spec.ts
```

这套流程会覆盖：

## 11. 当前边界、已知限制与注意事项

虽然项目整体功能已闭环，但仍存在一些明确边界：

- 学生注册已经是真实写入流程，但仍属于内部预览级能力。
- 当前尚未实现邮箱验证、密码找回、验证码、注册防刷等公开化能力。
- 站外告警投递依赖环境变量配置；若未配置 SMTP / Webhook / Slack，则相关能力会显示为不可用。
- Supabase pooler 在长链浏览器测试中仍可能出现瞬时连通性抖动。
- 读请求已做一定重试保护，写请求仍保持 fail-fast，以避免重复业务动作。
- 模拟算法已经完成业务闭环，但仍存在进一步校准空间，尚未完成最终教学口径精调。
